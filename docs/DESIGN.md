## 1. 実現可能性

| 項目 | 判断 | 補足 |

## 2. Safari で使うカメラ API

| API | 用途 | 注意点 |
|---|---|---|
| `navigator.mediaDevices.getUserMedia` | カメラ映像の取得 | `facingMode: environment`、`width/height/frameRate` を `ideal` で要求。拒否時は案内を表示 |
| `MediaStreamTrack.getSettings / getCapabilities` | 実際の解像度・fps・上限の確認 | 診断画面に表示 |
| `applyConstraints` | fps が要求値に届かないとき再要求 | 効くかどうかは端末依存 |
| `HTMLVideoElement.requestVideoFrameCallback` | 新しいフレームごとに処理 | `captureTime` `mediaTime` `presentationTime` を受け取る |
| `enumerateDevices` | カメラ（レンズ）の選択 | 許可後でないと名前が出ない |
| `CanvasRenderingContext2D.drawImage / getImageData` | 画素の取り出し | 測定範囲だけを縮小して取り出す |
| `navigator.wakeLock` | 計測中の画面消灯防止 | 非対応なら何もしない |
| `speechSynthesis` | 結果の読み上げ | 最初のタップ内で有効化が必要 |

### フレーム時刻の扱い

速度は「距離 ÷ 時間」なので、時刻の誤差はそのまま速度の誤差になります。

- フレームレートが一定とは仮定しません。フレームごとの時刻をそのまま使います。
- 時刻情報は `captureTime`（撮影時刻）→ `mediaTime` → `presentationTime` → 受信時刻 の順に優先し、最初の 12 フレームで「実際に値が進んでいるもの」を選びます。
- カメラ診断で、各時刻情報の間隔のばらつきを比較できます。

**要実機確認**：iPhone の Safari が `captureTime` を返すか、`mediaTime` がどの程度正確か。PC の Chromium では `captureTime` が使えることを確認しましたが、Safari の挙動は別です。

## 3. ボールの速度測定の設計

処理の流れ：

```
映像 → 測定範囲を縮小して取り出す → 白いボール候補の検出 → 実寸座標へ変換 → 追跡 → 速度の当てはめ → 有効性の判定
```

### 3.1 ピクセル → メートル（`js/core/homography.js`）

マットの両脇に置いた目印（4点または6点）の画像上の位置と、メジャーで測った実寸から、ホモグラフィ（遠近補正の式）を求めます。カメラが斜めから見ていても、マット面上の位置をメートルで得られます。

**6点を既定にした理由（シミュレーション結果）**

目印を合わせるときのタップ誤差が速度に与える影響を、400 回の試行で調べました（横からの配置、目印の幅 30cm、長さ 150cm、映像 1280×720）。

| 校正方法 | タップ誤差 | 速度誤差（中央値） | 速度誤差（95%点） |
|---|---|---|---|
| 4点 | ±1px | 0.86% | 2.09% |
| 4点 | ±2px | 1.69% | 4.08% |
| 6点 | ±1px | 0.27% | 0.68% |
| 6点 | ±2px | 0.37% | 1.09% |

横から見ると幅 30cm が画像上で数十 px にしかならず、4点では遠近の推定が不安定になります。中間の2点を加えると、進行方向の縮尺が直接拘束されて 3〜4 倍安定します。

**レンズ歪み**：補正はしていません。6点校正では、6点が1つの平面の式に乗らない量（食い違い）を mm で表示します。歪みやタップミス、寸法の入力ミスがあるとこの値が大きくなります。対策は、1x カメラを使うこと、測定範囲を画面の中央寄りに置くことです。

### 3.2 ボール中心の高さの補正

校正はマット面（高さ 0）で行いますが、画像に写るボールの中心は半径 21.3mm だけ浮いています。高さ h のカメラから見ると、浮いた点はマット面上では

```
見かけの位置 = N + (実際の位置 − N) × h / (h − r)      N：カメラの真下の点
```

に見えます。カメラ高さ 1m で約 2.1% の拡大です。

- 距離と速度は、カメラの向きに関係なく一律に h/(h−r) 倍に見えます → (h−r)/h を掛けて補正します。
- 位置そのもの（スタートラインをいつ通過したか、どこで止まったか）を直すには N が必要です。N はホモグラフィから推定します（画素が正方形・光軸が画像中心という仮定）。
- 推定したカメラ高さと入力値が 35% 以上違う場合は、推定を信用せず距離だけの補正に切り替えます。校正画面には両方の値を並べて表示するので、設定ミスの発見にも使えます。

シミュレーションでは、補正なしだと約 +1.7%、距離だけの補正だと遅い球で約 −1%、位置ごと補正すると 0.3% 以内でした。

### 3.3 ボール検出（`js/core/detector.js`）

白色判定だけでは誤検出するため、次を組み合わせます。

| 条件 | 内容 | 除外できるもの |
|---|---|---|
| 明るさ | 輝度がしきい値以上 | マット、暗い床 |
| 無彩色 | RGB の最大と最小の差が小さい | 緑のマット、肌、色付きの目印 |
| 動き | 背景より一定以上**明るくなった**画素のみ | 最初からある白い物、影、暗いパターヘッド |
| 形と大きさ | その位置で期待されるボール直径に合う塊 | 大きな反射、細い線、ノイズ |
| 測定範囲 | 範囲の内側だけを見る | 範囲外の人や物 |
| 移動の連続性 | 追跡側で判定 | 単発の誤検出 |

背景は計測開始時に取得し、待機中はゆっくり更新します。止まった白い物体は約1秒で背景に取り込まれます。追跡中は背景を固定します。

### 3.4 追跡（`js/core/tracker.js`）

- スタート側から進行方向へ、一定以上の速さで 3 フレーム連続して動いたものだけを打球とみなします。
- 追跡中は、直前の速度から予測した位置の近くにある候補だけを採用します。急な方向転換・速度の急増は不採用です。
- 複数の仮追跡を同時に持つので、止まっている白い物体に引きずられません。
- 終了条件：ゴールラインを通過／横へ出た／範囲内で停止／見失い／時間切れ。
- スタートラインの手前だけで終わった動き（素振りなど）は、結果を出さずに捨てます。

### 3.5 速度の計算（`js/core/kinematics.js` `js/core/analysis.js`）

観測区間では減速度が一定とみなし、位置と時刻の列に

```
s(t) = s0 + v0·t − a·t²/2
```

を最小二乗で当てはめます。フレームが欠けても、時刻が正しければ結果は偏りません。

出力する値：

- **入口速度**：スタートライン通過時の速度（画面の大きな数字）
- 区間中央の速度、出口速度、平均速度
- 減速度と、その推定誤差
- 進行方向の角度
- 範囲内で止まった場合は停止位置

**突発的な外れ値への対策**

カメラ映像では、ときどき 1 フレームだけ時刻と画像が数 ms 食い違います（処理の遅れなど）。2 m/s の球なら 5ms のずれは位置 1cm の誤差です。そこで、当てはめの残差が突出した点を取り除いて当てはめ直します（中央絶対偏差にもとづく反復除去）。取り除いた点が 15% を超えた場合は、結果を無効にします。

**打ち出し直後の滑り（スキッド）**

打った直後のボールは滑りながら回転を得ます。この間の減速は転がりの数倍です。区間内で減速度が切り替わるモデル（2区間モデル）も当てはめ、次の条件をすべて満たす場合だけ採用します。

- 1区間モデルより明確に良い（BIC の差が 10 以上）
- 滑り区間に 5 点以上ある
- 滑り中の減速度が 1.5〜7 m/s² で、転がりより 1 m/s² 以上大きい
- **先頭の点を 1〜2 個抜いて計算し直しても、同じ結論・同じ入口速度（2% 以内）になる**

最後の条件は、PC ブラウザでの検証中に見つかった不具合への対策です。最初のフレームの時刻が数 ms ずれただけで「強い減速のあと緩やかになった」と解釈され、入口速度を 27% 誤った結果が「有効・信頼度 96」で出ました。先頭の点を抜くと滑りの証拠が消える場合は外れ値による見かけの滑りと判断して 1区間モデルを使い、証拠は残るが値が食い違う場合は判別不能として無効にします。

残る限界：

- 切り替わりがスタートラインのすぐ近く（1〜4 フレーム）にあると滑りを検出できず、入口速度は「転がりの式を手前に延長した値」になります。滑っている最中の実際の速度より数%低い値ですが、距離換算に必要なのは転がりの速度なので、実害は小さいと考えています。
- 滑りが区間内にあり、かつ時刻のずれが切り替わり付近に重なると、入口速度に最大 2〜3%、出口速度に最大 2% 程度の誤差が出ることをシミュレーションで確認しています。

どちらも、スタートラインをボールから 30cm 以上（強く打つ場合はさらに）離し、滑りが区間に入らないようにすれば避けられます。

### 3.6 無効にする条件

次のいずれかに当てはまる結果は「計測失敗」とし、数値を確定しません。しきい値は `js/config.js` の `validity` にあります。

フレーム数不足／観測距離不足／途中で見失った／検出できなかったフレームが多い／フレーム間隔が 0.1 秒超／fps が低すぎる／軌道が直線から外れている／当てはめ誤差が大きい（距離で 3mm、または時間換算で 1.5ms 相当を超える）／残差が滑らかに偏っている（動きがモデルに合っていない）／外れ値が多すぎる／速度が範囲外／加速している／推定誤差が大きい／逆方向／画面全体が変化した／スタートライン付近で検出できなかった／スタートライン付近の動きを確定できない

有効な結果には、当てはめ誤差・見失い率・フレーム数などから 0〜100 の信頼度を付けます。

## 4. 9フィート換算の数理モデルと必要な校正（Phase 2 の設計）

Phase 1 では実装していません。ここでは方針と、決めるべきことを整理します。

### 4.1 スティンプ値の意味

スティンプメーターは、ボールを一定の速さ（約 1.83 m/s ＝ 6.00 ft/s）で平らなグリーンに送り出し、転がった距離をフィートで読む器具です。9 フィートは**速度ではなく距離**です。

減速度が一定だと仮定すると、スティンプ S フィートのグリーンの減速度は

```
a_S = v_s² / (2 × S × 0.3048)        v_s ≒ 1.83 m/s
a_9 = 1.83² / (2 × 2.7432) ≒ 0.610 m/s²
```

**確認が必要な点**：送り出し速度は資料によって 1.83〜1.94 m/s の幅があります。1.94 を使うと a_9 は約 12% 大きくなり、推定距離が約 11% 短くなります。Phase 2 では値を設定で変えられるようにし、根拠の資料を明記します。

### 4.2 推定距離の基本式

測定点（位置 y_m）で、純転がりの速度 v_m が得られたとします。

```
推定距離 D = d0 + y_m + v_m² / (2 × a_9)

d0  ：ボールを置いた位置からスタートラインまでの距離（設置時に入力）
y_m ：スタートラインから測定点まで
```

つまり「測定点から先は 9 フィートのグリーンを転がる」とみなします。測定点は、滑りと転がりの切り替わり点ではなく、転がり区間の内側（例：ゴールライン通過時）に取ります。切り替わり時刻の推定には 1 フレームぶんの不確かさがあり、その時点の速度は数%ぶれるためです。この式では、マット自体の転がり抵抗は測定点より手前の区間にしか影響しません。10m のパットなら、手前の 0.5〜1m ぶんです。

速度誤差と距離誤差の関係は D ∝ v² なので、**速度 1% の誤差が距離 2% の誤差**になります。10m で ±1m（±10%）の判定をするには、速度を ±2% 程度以内で測れている必要があります。

参考：9 フィートのグリーンで各距離に必要な速度（転がりのみ、上の式から）

| 目標 | 3m | 5m | 7m | 10m | 15m |
|---|---|---|---|---|---|
| 必要な速度 | 約 1.9 m/s | 約 2.5 m/s | 約 2.9 m/s | 約 3.5 m/s | 約 4.3 m/s |

15m では 60fps でも 1 フレームに約 7cm 進み、1.5m の区間で約 21 フレームしか取れません。30fps に落ちると約 10 フレームで、有効条件（8 フレーム以上）の下限近くになります。また、この速さのボールは室内ではマットの終端を強く越えます。**15m ステージが実用的かは実機で確認が必要**です。

### 4.3 この式が置いている仮定と、検証方法

| 仮定 | 崩れた場合の影響 | 検証・校正の方法 |
|---|---|---|
| グリーン上の減速度は速度によらず一定 | 実際の芝は低速ほど減速が大きい傾向がある（資料では 10% 程度の変動）。長いパットで推定が短めに出る可能性 | 実際の練習グリーンでこのアプリを使い、入口速度と実際の停止距離を記録して a(v) を確かめる |
| 測定点で純転がりになっている | 滑っている途中の速度を使うと距離を過大評価する | スキッド検出の結果を使う。スタートラインをボールから離す |
| 送り出し速度 1.83 m/s | 上記のとおり約 11% の差 | 資料の確認 |
| 平坦 | 傾斜があると成り立たない | マットの設置面を確認。往復で測って平均する |

**校正の手順（Phase 2 で実装する内容）**

1. マットの転がり抵抗 a_mat を求める。弱く打って範囲内で止め、入口速度 v と停止位置 d から a_mat = v²/(2d)。計測ログの「実際に転がった距離」はこのために用意しています。
2. a_mat は、ボールを置いた位置から測定点までの区間の補正（打ち出し直後の速度の逆算）に使う。
3. 補正係数は実測の回帰で決め、根拠のない係数は置かない。校正データが足りない間は「未検証」と表示する。

### 4.4 ゲームでの扱い

仕様書のとおり、精度の検証が済むまでは「未検証」と明示し、正式な勝敗判定と区別します。

## 6. 検証結果

### シミュレーションテスト（`npm test`）

合成映像（真値の分かる映像）を、画素 → 検出 → 追跡 → 速度計算まで通して真値と比較しています。**実機カメラのテストではありません。**

| 条件 | 結果 |
|---|---|
| 横から / 後方から（縦長） | 入口速度の誤差 1% 未満 |
| 1280×720 を半分に縮小して処理 | 1% 未満 |
| フレーム欠落・撮影間隔のゆらぎ（時刻は正しい） | 1% 未満 |
| 記録時刻に ±3ms の誤差 | 1.5% 未満（当てはめ誤差が増え、信頼度が下がる） |
| 30fps | 1% 未満 |
| 速い球 4.5 m/s・遅い球 1.6 m/s | 1.5% 未満 |
| 範囲内で停止 | 停止位置 1cm 以内 |
| 最初からある白い物体・後から置かれた白い物体 | 誤検出なし |
| 暗い／白いパターヘッドが追ってくる | ボールの速度を返す |
| 照明の急変・ボールなし・範囲外の球 | 結果を出さない |
| 8% のフレームで時刻が 5ms ずれる（1点目・3点目を含む） | 滑りの誤認なし。有効な結果はすべて 1.5% 未満 |
| 15% のフレームで時刻が 8ms ずれる | 大半を無効と判定。有効とした結果も 3% 未満 |

合成映像は理想的な条件（均一な照明、歪みなし、正確な時刻）です。実機ではこれより悪くなります。

### PC ブラウザでの確認

Chromium に合成映像を「カメラ」として与え、`getUserMedia` からの経路を通しました。

- 最初の版では、十数打のうち 1 打で入口速度を 27% 誤る不具合が出ました（3.5 節の「先頭の点を抜いて確かめる」対策の原因）。
- 対策後は、有効と判定された 21 打すべてが真値の ±0.25% 以内でした。1 打あたり 0〜8 フレームが外れ値として除かれています。
- 処理落ちで 0.17 秒の空白が出た打球、計測開始が打球の途中だった打球は、無効と判定されました。

この環境は GPU のない PC で、iPhone とは処理速度も時刻の性質も違います。あくまで「処理経路が通ること」と「乱れた時刻への耐性」の確認です。
